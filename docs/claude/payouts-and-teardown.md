Words like "above", "below" or "this file" refer to the original single CLAUDE.md; the docs index at the end of CLAUDE.md says where each section now lives.

## Three tiers of data access — continued (payouts, FKs, fixtures)

**The `rep_payout_*` tables are the deliberate exception to `log_cross_agent_change()`, and the reasoning is worth knowing before you "fix" the omission.** `rep_payout_rows` carries `agent_id` and would work with that trigger unchanged — but nobody except an admin can write the table at all (no insert policy, admin-only update and delete), so `actor is distinct from row_agent_id` is true for *every* write. One forty-row import would produce forty `cross_agent_insert` rows, and it still could not record what a figure changed *from*, because `audit_log` has no detail column. So the trail is split by granularity instead: `audit_log` per committed batch and per deleted period, and `rep_payout_row_history` per value change, where a before and an after actually fit. The other three payout tables have no `agent_id` at all, which is the `support_ticket_replies` trap — that function would read NULL and log everything.

`rep_payout_rows.rep_payout` is a **stored generated column** (`round(residual_income * rep_split_pct / 100, 2)`), so it is null whenever either input is null and cannot be written directly. Null means "not worked out yet", never zero, and every total, export and summary has to keep that distinction. `average_ticket` is `check >= 0` because a negative there is a parse error. **A negative `volume` is allowed only on a line marked `volume_confirmed_negative`, and the marker only on a negative volume** (`rep_payout_rows_volume_check`, `20261030120000`, memo §2.4): the marker is written by commit v3 (phase 8) for a row whose `bad_numbers` warning the admin confirmed, so the column says which lines entered that way; no client can set it (no column grant). Zero volume stays allowed; `total_cost` and `residual_income` are deliberately **signed**, because clawbacks are real and a constraint rejecting one turns valid processor data into an unexplainable blocked import.

**`authenticated` holds UPDATE on exactly two `rep_payout_rows` columns, `residual_income` and `rep_split_pct`** (`20261014160000`, the `quotes.status` arrangement): those are all the inline cell and the bulk split write. Every other column is written by `commit_residual_import` / `set_shared_residual` (definer), FK `SET NULL` actions (owner) or the service role, none of which the grant reaches — so an admin's session writing `merchant_name`, `volume` or a share column gets `42501`, not a silent filter. A new client path that edits another column needs a grant line or a definer RPC, not a policy. **The merge key is a PARTIAL unique index since phase 5** (`20261016160000`): `rep_payout_rows_import_merge_key` on `(period, agent_id, mid) where line_kind = 'import'` — **since `20261030120000` `(period, processor, agent_id, mid) NULLS NOT DISTINCT where line_kind = 'import'`** (NULLS NOT DISTINCT so today's NULL-processor lines still merge; both commits write the batch's processor) — which replaced the `unique` constraint and dropped `rep_payout_rows_import_lines_only` in the same transaction. Adjustment lines (written only by `post_share_correction()`, `20261016161000`) sit outside it. Two consequences to carry everywhere: **every `on conflict` on this table must name `(period, processor, agent_id, mid)` and say `where line_kind = 'import'`** or Postgres cannot infer the index and the statement fails; and **every "is this month committed" read must look at import lines only** — v2's `line_not_shared`, the three share RPCs, the posting-month computation and the parser's `mid_in_other_batch` and `payee_changed` reads all do, because an adjustment sits in a month nobody has committed yet. An adjustment carries no residual, rate, volume or batch (`rep_payout_rows_adjustment_no_figures`), so `PayoutBulkSplit` filters to import lines. The export marks one `Line = Adjustment`. Until phase 7 the parser skipped such rows on a re-import (`rep_payout_batches.adjustment_rows_ignored`); since phase 7 (`docs/design/intake-and-reports.md`) the export is not an import format at all — the parser reads the processor's six columns and refuses a file carrying `Agent #` or `Rep payout` as a CRM export — so a correction still never becomes an import line. `tests/rls/import-merge-key.test.ts` pins the catalog diff and the migration's own nothing-moved check.

**Shared accounts on the screens (phases 6–7, `docs/design/residual-splits.md`).** The merchant page carries the admin's share card (`components/merchant-share-card.tsx`: set in rep-percent terms "40 + 10" totalling the merchant's rate — 50 for most — end, cancel, correct) and, for a party who can open the merchant — in practice the signer — a one-line notice from `my_share_partners()`. The correction control shows **"This will post to <month>" before anything is written**, from `share_correction_posting_period()` (`20261019130000`, read-only, admin-only definer). **The posting-month rule exists once**: `post_share_correction()` was re-created to *call* that function, and gained `expected_posting_period_input date default null` — given and no longer matching (a commit landed between the preview and the click), the post is refused PT409 rather than landing in a month nobody confirmed. Its six-argument signature was **dropped**, not overloaded (the `create_quote_version()` trap). On `/payouts/[period]` each shared line gets a full-width marker row beneath it (cells stay nowrap, so the money columns stay on screen); the admin's carries both parties and the account residual and, on the signer's line, `components/shared-residual-control.tsx` → `set_shared_residual()`, which replaces the per-line residual editor on both lines (the guard refuses that edit anyway); the partner's split is read-only. **A rep's partner line names the merchant as plain text**, never a link to a page they cannot open. `PayoutBulkSplit` skips partner lines (`.or("share_role.is.null,share_role.eq.primary")`) — the filter matters for a rep who is a partner on one account and has ordinary lines too, whose group would otherwise be refused whole. The statement marks each shared line "Shared account with <partner> · your share X% †" with a footnote; the export adds `Account share` last (the row's **own** share, blank when unshared; the parser's exact header lookup ignores it). Every control these phases added is 44px tall; the older payout controls (`PayoutFigureCell`, the bulk split's 28px input) are not, which is a recorded follow-up. Not on any hosted project yet.

**`rep_payout_batches` is the same arrangement with one column: `authenticated` holds UPDATE on `status` only** (`20261016140000`, phase 4b). Abandon is the one client writer; `skipped_rows` and `skips_acknowledged_at` are written only by the commit (v2 wrote skips; v3, since `20261030160000`, always writes `[]`) and `acknowledge_residual_skips()` (definer, `is_admin()` first, refuses a second acknowledgement, audit fails closed), so an admin's PATCH cannot clear a skip record. **Which status change that grant allows is a trigger's job** (`guard_batch_status_transition()`, `20261016170000`): when `current_user = 'authenticated'` the only update admitted is `review -> abandoned` (PT409 otherwise), so a client cannot move a committed batch back to review and re-commit a month, or mark one committed with nothing imported. The definer commits and acknowledgement run as the owner and the parser and file-url functions as the service role, so none of them is touched. Who acknowledged is in `audit_log` only — no `skips_acknowledged_by` column, so the `profiles` FK count stays twenty-five. **Since `20261030120000` a batch also carries `processor` + `period` (nullable together until phase 7's upload sets them; the month is the 1st, not in the future, not over 24 months back, checked by the `guard_payout_batch_period()` trigger), and `rep_payout_batches_one_committed_per_month` makes a second committed batch for one (processor, month) impossible; `replaced` is a definer-only status that needs `replaced_by_batch_id`. `payout_period_closures` (Mark paid) is admin-SELECT-only, never updated, and audited per insert/delete by its own fail-closed trigger (`close_payout_period` / `reopen_payout_period`); phase 9's functions write it.** The commit button calls v2 and lands on the batch page, which is the commit result; the old `commit_residual_import` stays only for an app version still deployed somewhere, and refuses any batch a share covers.

**Deleting a user requires clearing five payout FKs first**, and all five are `NO ACTION`: `rep_payout_rows.agent_id`, `rep_payout_import_rows.agent_id`, `rep_payout_batches.imported_by`, and both `rep_payout_row_history.agent_id` and `.changed_by`. Exactly the trap `audit_log.actor_id` sets, with five doors instead of one — and it has already been walked into once: a teardown deleted a profile without clearing staging rows, the delete failed on the FK *unchecked*, and the surviving rep then resolved an agent number the next run expected to be unknown, which presented as a parser bug. Clear all five before `deleteUser`, and check the error.

And know the real total while you are there: **twenty-five columns reference `profiles(id)`, and twenty-four of them are `NO ACTION`** (`profiles.manager_id`, added 2 Oct 2026, is the single exception at `on delete set null` — see below) — the five payout ones, `user_import_batches.imported_by`, `audit_log.actor_id`, `support_ticket_replies.author_id`, both `bug_reports` columns, `agent_id` on each of the seven owner tables, the two marketing ones added 2 Oct 2026 (`marketing_materials.uploaded_by`, `marketing_material_events.agent_id`), `quotes.agent_id` (`20261002194500`), `business_documents.uploaded_by` (`20261013120000`), and `merchant_rep_shares.primary_agent_id` + `.secondary_agent_id` (`20261014130000`; shares must be cleared by merchant first too, because `merchant_id` is `ON DELETE RESTRICT`). Any single leftover row blocks the delete, so a hand-written teardown list is permanently one table behind: `scripts/seed-local-users.mjs` carried two entries and broke the moment `seed-dev-payouts.mjs` gave the rep a ledger row. It now holds all nineteen, in FK-safe order, with the `pg_constraint` query to regenerate it in a comment — copy that list rather than reinventing it. The failure mode is worth recognising: an unchecked `deleteUser` that fails on an FK leaves the user in place, and the next `createUser` reports `email_exists` (422), which names the one thing that is not wrong.

**There are now FOUR teardown lists, and they drift independently** — `scripts/seed-local-users.mjs` (`PROFILE_REFERENCES`), `tests/live/helpers/stack.ts` (`clearPayoutRows` + `clearUserImports` + `clearMarketingMaterials` + `clearBusinessDocuments`), `e2e/fixtures/seed.ts` (`clearImportedUsers`), and `seed-dev-local.mjs` (its own `PROFILE_REFERENCES`). That fourth one went undocumented for a month and carried eight entries while the canonical list had eighteen, so `node seed-dev-local.mjs` died with `email_exists` on any stack where `seed-dev-payouts.mjs` had run — the exact trap this paragraph describes, walked into by the one list nobody had written down. Fixed 2 Oct 2026, and its `deleteUser` is now checked.

`tests/rls/user-imports.test.ts` asserts the count is exactly twenty-five and that the only non-`NO ACTION` one is `profiles.manager_id`, **by name** — a bare count of exceptions would let a twenty-second column arrive with an `ON DELETE` of its own and pass as the known one. So adding a twenty-fourth reds a test rather than a teardown — but the test only counts them, it cannot know which list forgot one. Update all four together.

**The two marketing columns cannot be two more rows in the flat lists**, and that is worth knowing before adding the next table that looks like them. A material uploaded by one admin can carry events logged by a DIFFERENT rep, and `marketing_material_events.material_id` is `NO ACTION` too — so deleting by `uploaded_by` alone fails on somebody else's row, naming `marketing_materials` while the row actually in the way belongs to a rep the teardown was never asked about. Events are cleared by material and then by actor, and only then the materials. `clearPayoutRows` already had the same shape for the same reason.

**`manager_id` is in all three lists even though it cannot block a delete**, and it is handled differently in each: `on delete set null` means Postgres would clear it unprompted, so these clear it with an **UPDATE, not a DELETE** — the row holding the pointer is a *different* rep's profile, which is also why it is not an entry in `PROFILE_REFERENCES` (that list deletes rows). The failure it guards against is the quiet one: a seeded reporting line vanishing from a surviving persona with nothing reporting that it happened.

**SheetJS is pinned to `https://cdn.sheetjs.com/xlsx-0.20.3/package/xlsx.mjs`, not `npm:xlsx`** — in `parse-residual-import/deno.json` and as the devDependency that builds test fixtures. npm's latest is 0.18.5 and carries two high-severity advisories (prototype pollution, ReDoS) fixed only in SheetJS's own later builds, since they stopped publishing to npm. Don't "simplify" it back to `npm:xlsx`. The remote-URL import is verified under `functions serve`; whether it survives `functions deploy` is untested, and the fallback is vendoring the one `xlsx.mjs` file, not downgrading.

Fixtures for these tables live in `seedPayouts()`, **not** `seed()`. Same reason `seed()` sets no `agent_number`: it is also run against a migration subset that predates them (`tests/rls/deactivation.test.ts` calls it with `createTestDb([INITIAL_MIGRATION])`), and anything it touches that a prefix has not created yet fails those suites with `relation does not exist`, pointing nowhere near the cause. `seedPayouts()` returns the ids it created rather than letting tests hardcode them, because `resetData()` clears these tables through the `cascade` from `profiles` without naming them — so their sequences are never restarted and the ids drift upward run after run.

**Every new batch needs a processor and a month** (`20261030140000`), inside the import window and, once committed, the only committed batch for its pair. A hermetic fixture inserts one with `insertBatch()` (a free month from `freeBatchMonth()`, the column left out on a database replayed to before it); `seedPayouts()` gives its two batches `SEED_BATCH_PROCESSOR` and months relative to now, and tags its ledger lines with the same processor so a test batch re-importing one lands on the same merge key. e2e fixtures take a slot from `freeBatchSlot()` in `e2e/fixtures/seed.ts`. A fixed month would start failing in two years, as the window moves.

Two consequences worth knowing before you write a test or a fixture. **Service-role and owner writes are logged with `actor_id = null`**, since neither has an `auth.uid()` — that is wanted for real server writes, but it means any fixture that seeds these tables as the platform owner stamps a `cross_agent_insert` per row. `tests/helpers/db.ts` `seed()` clears `audit_log` at the end for exactly that reason, and the live-suite teardowns clear the rows their own inserts *and deletes* generate. **And expect deliberate duplication**: `approve_pre_app` / `decline_pre_app` write their own row and also mutate a rep's `pre_apps`, so one event yields two rows at different granularities. Assert on `action` rather than on row counts.

## Commit v3, the merchant's rate, and shares under the owner rule (phase 8, `20261030160000`)

**`commit_residual_import_v3(batch_id_input int, confirmed_input text[])` is the commit the app calls** (`components/residual-commit-button.tsx`, passing the warning types answered yes). `commit_residual_import_v2` is dropped; `commit_residual_import(int)` stays, with its coalesce merge, only because prod's deployed app calls it, and goes in phase 13.

- **One transaction, locked**: the batch row `for update`, an advisory lock on its processor-month (two batches for one pair cannot both pass "nothing committed yet"; the unique index `rep_payout_batches_one_committed_per_month` is the backstop), the share lock, and `for share` on every merchant the file names.
- **Re-derived, never trusted from staging**, each a PT409 that lists what it found: a row read for another month than the batch's, a blank, repeated or unknown MID, an Income Type other than Residuals, a missing figure, **an owner or MID that changed after the read** (refused, never re-paid: "Read it again"), a merchant with no rate, a MID that already has an import line that month under any processor, and a covering share whose signer is not the owner or whose shares do not total the rate.
- **Warnings recomputed** (the parser's `rowWarnings`; the live suite pins that the types the parser stored are exactly the ones v3 demands, via the error's DETAIL). A type present and not in `confirmed_input` refuses; the batch keeps `confirmed_warnings` (`{"bad_numbers": [4, 7]}`).
- **Never merges.** Plain inserts, no `on conflict`. A second file for a committed processor-month is the replace (phase 9); after Mark paid, an adjustment line.
- **The money is the merchant's rate**: `rep_split_pct = merchants.split_agent_pct` on every line, so `rep_payout` is `round(R × rate / 100, 2)` and the company keeps the rest; a house merchant at 0 still gets its line (payout 0.00, volume and net shown). A shared month is the signer's line (volume, residual `R − p`) and the partner's (no volume, `p = shared_part(R, b, a + b)`); with `a + b` = the rate, the existing generated column pays the pair `T` exactly, the signer absorbing the odd cent. `volume_confirmed_negative` is set exactly where volume < 0, which only a confirmed `bad_numbers` lets through.
- **Overrides (phase 10) plug in at step 6** of the function, after the import lines: their own debit/credit lines, counted in the `overrides` key the result already returns. Nothing about `T` changes.
- Audit: one `commit_residual_import` row (who); `committed_at` (when). No `committed_by` column: it would be a 26th `profiles` FK and a fifth entry in every teardown list.

**The merchant's rate** (`merchants.split_agent_pct`, the snapshot `approve_pre_app()` copies from the pre-app): `merchants_split_zero_to_fifty` (validated; NULL with NULL, or 0-50 with the company half 100 minus it). **`set_merchant_split(merchant_id, rate)` is the only write path** — the `set_rep_split` shape, audited `set_merchant_split`, refused while the merchant has a live share — and `guard_merchant_split_and_owner()` refuses every other UPDATE of the two columns, an admin's and the owner's included (flag `tapswipe.merchant_split_write`, set only by that function). INSERT is not guarded: a hand-made merchant starts with no rate, and v3 refuses it until an admin sets one (the Split control on the merchant page, `components/merchant-split-cell.tsx`). The merchant form has no split input any more.

**Shares under the owner rule.** `set_merchant_rep_share()` refuses a signer who is not the merchant's current owner, a merchant with no rate or a rate of 0, and shares that do not total the merchant's rate; the table CHECK (`merchant_rep_shares_total_rep_side`, and the ledger's `rep_payout_rows_share_snapshot`) is relaxed to `<= 50`, the outer bound. Moving a merchant (`agent_id`) while a share is live is refused by the same trigger: PT409 "This merchant has a shared-account split. End it before moving the merchant." **Live** = could still pay a month: open-ended, or ending after the latest month with an import line for that merchant (`merchant_has_live_share()`, no client EXECUTE). `post_share_correction()` is unchanged: its two shares are still a ratio typed out of 50, applied to the signer's payout, so it works at any rate.

## Why `commit_residual_import` is an RPC

Moved verbatim from CLAUDE.md's "Three tiers" §3 on 26 Oct 2026. It is an RPC and **not** an eighth Edge Function on purpose: supabase-js has no client-side transaction, so a function would insert ledger rows, delete staging rows and flip the batch status as three round trips with a real window where a period is half-imported. It also sidesteps PostgREST's row cap (`insert … select` has none), gets a fail-closed audit row for free, and keeps `auth.uid()` — so the history rows the merge triggers name the committing admin.
