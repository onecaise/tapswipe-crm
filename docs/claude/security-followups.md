# Security follow-ups: recorded, not built

Items from the October 2026 outside review (and found while fixing it) that were deliberately **not** built on branch `security-fixes`. Each has a severity, the evidence for it, and a suggested fix. The fixes that were built are in `docs/claude/security-fixes.md`.

## Block a staged residual row whose merchant's MID changed since the file was read

- **Severity:** Low (defence in depth; the attack it covers needs an admin since 20261021120000).
- **Evidence:** `commit_residual_import_v2` finds the share for a staged row with `left join merchants m on m.mid = r.mid_raw` — the merchant's MID **at commit**. `parse-residual-import` already stores `merchant_id` on each staged row, resolved from `mid_raw` when the file was read. If the merchant's MID changes between the read and the commit, the row matches no merchant, commits as an ordinary line, and a shared account is paid unshared. Phase 1 made MID admin-only and audited every change (`merchant_mid_changed`); an admin padding or correcting a MID during review still produces this.
- **Suggested fix:** in `commit_residual_import_v2`'s guards, refuse the batch (PT409, before the plan) when any staged row has `merchant_id is not null` and that merchant's current `mid is distinct from mid_raw`, with a sentence like "A merchant's MID changed after this file was read. Read the file again." Mirror it in `parse-residual-import` as a blocker so the review screen shows it, since "read again" already re-resolves `merchant_id`. Tests: the phase 1 attack test, re-run as an admin, must refuse instead of committing unshared.
- **Rejected alternative:** storing the MID on `merchant_rep_shares` and matching on it. A legitimate MID change would then detach the share in the other direction, and it needs two sources of truth kept in step. Reasoning in `docs/claude/security-fixes.md`, phase 1.

## Secrets writes on a non-draft pre-app are guarded only by the Edge Function

- **Severity:** Low (no client path to the tables; the function's check is tested since phase 2).
- **Evidence:** `submit-pre-app-secrets` checks `status !== "draft" && !isAdmin` and returns 409 before `supabaseAdmin` writes `pre_app_owner_secrets`, `pre_app_banking_secrets` or `pre_app_terminal_secrets`. Nothing in the database enforces the same rule on those three tables: the function writes as service role, which has no `auth.uid()`, so a trigger cannot tell an admin's correction from a rep's late change. A future function, or an edit that reorders the guard, would write a submitted pre-app's secrets unchecked.
- **Suggested fix:** if a database backstop is wanted, have the function write through a `security definer` RPC that takes the caller's id as an argument verified against the JWT (or set a transaction-local `tapswipe.secrets_actor` the trigger reads), and add a status trigger to the three tables that admits only a draft or an admin actor. Not worth it while one function is the only writer and its branch is pinned by `tests/live/pre-app-secrets.test.ts`.

## A merchant hand-off may need "the current owner can read notes on the merchant they own"

- **Severity:** Not a vulnerability; a product gap, recorded so the fix is the right shape when it is wanted.
- **Decision (Owen, 21 Oct 2026):** a merchant reassignment carries **nothing** but `merchants.agent_id`. Notes, tasks, proposals (`quotes`) and `merchants.pre_app_id` stay as they are.
- **Evidence:** `notes`, `tasks` and `quotes` are scoped by their OWN `agent_id` (`(agent_id = auth.uid() and is_active_agent()) or is_admin()`), not by the merchant's owner. After an admin moves a merchant from rep A to rep B, B opens the merchant and sees none of A's notes, tasks or proposals on it; A can no longer open the merchant but still sees their own notes and tasks filed against it (`/notes`, `/tasks`). Pinned by "reassigns: the old owner loses sight of it…" in `tests/rls/merchants-admin-only-writes.test.ts` (the merchant half) and the notes/tasks policies.
- **Suggested fix, if a hand-off needs history:** add a **read** policy — the current owner of a merchant may SELECT notes (and, if wanted, tasks) whose `owner_type = 'merchant'` and whose merchant they own now — rather than rewriting `notes.agent_id` to the new owner. Moving authorship is the wrong fix: `notes` is append-only by design (no UPDATE policy, and the UPDATE grant revoked in 20260812143407), so a note's `agent_id` records **who wrote it**, and the trail is only worth anything if nothing — an admin's reassignment included — can change that after the fact. A read policy widens who can see a note without changing what it says or who said it. It would be a cross-book read, so it needs the same care as the other cross-book paths (`docs/claude/rpcs-profiles-audit.md`): `owner_type` in the predicate (ids collide across types), `is_active_agent()` on the branch, and a test that a rep who owns merchant 7 does not see notes on lead 7.

## `check_duplicates()` is a cross-book read with no audit and no limit

- **Severity:** Low to Medium (noticed while fixing `accounts_in_city`, phase 5; not in the review).
- **Evidence:** `check_duplicates()` is `security definer` over every rep's book, like `accounts_in_city()` was before 20261023120000. It answers free-text inputs (business name, phone, email, address, MID…) with a redacted match list, and writes nothing to `audit_log`. A rep can loop over candidate names or phone numbers and learn which exist in someone else's book. Its output is narrower than `accounts_in_city`'s (it warns about a match, it does not list a city's accounts), and the function must never become a block.
- **Suggested fix:** the phase 5 pattern: one `audit_log` row per call (`check_duplicates:<fields supplied>`, no values), and a per-rep hourly limit counted from those rows under an advisory lock. Size the limit from real use first; the pre-app and lead forms call it on blur, so it is far chattier than the city search.
