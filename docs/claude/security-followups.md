# Security follow-ups: recorded, not built

Items from the October 2026 outside review (and found while fixing it) that were deliberately **not** built on branch `security-fixes`. Each has a severity, the evidence for it, and a suggested fix. The fixes that were built are in `docs/claude/security-fixes.md`.

## Block a staged residual row whose merchant's MID changed since the file was read

- **Severity:** Low (defence in depth; the attack it covers needs an admin since 20261021120000).
- **Evidence:** `commit_residual_import_v2` finds the share for a staged row with `left join merchants m on m.mid = r.mid_raw` — the merchant's MID **at commit**. `parse-residual-import` already stores `merchant_id` on each staged row, resolved from `mid_raw` when the file was read. If the merchant's MID changes between the read and the commit, the row matches no merchant, commits as an ordinary line, and a shared account is paid unshared. Phase 1 made MID admin-only and audited every change (`merchant_mid_changed`); an admin padding or correcting a MID during review still produces this.
- **Suggested fix:** in `commit_residual_import_v2`'s guards, refuse the batch (PT409, before the plan) when any staged row has `merchant_id is not null` and that merchant's current `mid is distinct from mid_raw`, with a sentence like "A merchant's MID changed after this file was read. Read the file again." Mirror it in `parse-residual-import` as a blocker so the review screen shows it, since "read again" already re-resolves `merchant_id`. Tests: the phase 1 attack test, re-run as an admin, must refuse instead of committing unshared.
- **Rejected alternative:** storing the MID on `merchant_rep_shares` and matching on it. A legitimate MID change would then detach the share in the other direction, and it needs two sources of truth kept in step. Reasoning in `docs/claude/security-fixes.md`, phase 1.

## Secrets writes on a non-draft pre-app are guarded only by the Edge Function

- **Severity:** Low (no client path to the tables; the function's check is tested since phase 2).
- **Evidence:** `submit-pre-app-secrets` checks `status !== "draft" && !isAdmin` and returns 409 before `supabaseAdmin` writes `pre_app_owner_secrets`, `pre_app_banking_secrets` or `pre_app_terminal_secrets`. Nothing in the database enforces the same rule on those three tables: the function writes as service role, which has no `auth.uid()`, so a trigger cannot tell an admin's correction from a rep's late change. A future function, or an edit that reorders the guard, would write a submitted pre-app's secrets unchecked.
- **Suggested fix:** if a database backstop is wanted, have the function write through a `security definer` RPC that takes the caller's id as an argument verified against the JWT (or set a transaction-local `tapswipe.secrets_actor` the trigger reads), and add a status trigger to the three tables that admits only a draft or an admin actor. Not worth it while one function is the only writer and its branch is pinned by `tests/live/pre-app-secrets.test.ts`.

## A merchant hand-off may need "the current owner can read notes on the merchant they own"

- **Severity:** Not a vulnerability; a product gap, recorded so the fix is the right shape when it is wanted.
- **Decision (Owen, 21 Oct 2026):** a merchant reassignment carries **nothing** but `merchants.agent_id`. Notes, tasks, proposals (`quotes`) and `merchants.pre_app_id` stay as they are.
- **Evidence:** `notes`, `tasks` and `quotes` are scoped by their OWN `agent_id` (`(agent_id = auth.uid() and is_active_agent()) or is_admin()`), not by the merchant's owner. After an admin moves a merchant from rep A to rep B, B opens the merchant and sees none of A's notes, tasks or proposals on it; A can no longer open the merchant but still sees their own notes and tasks filed against it (`/notes`, `/tasks`). Pinned by "reassigns: the old owner loses sight of it…" in `tests/rls/merchants-admin-only-writes.test.ts` (the merchant half) and the notes/tasks policies.
- **Suggested fix, if a hand-off needs history:** add a **read** policy — the current owner of a merchant may SELECT notes (and, if wanted, tasks) whose `owner_type = 'merchant'` and whose merchant they own now — rather than rewriting `notes.agent_id` to the new owner. Moving authorship is the wrong fix: `notes` is append-only by design (no UPDATE policy, and the UPDATE grant revoked in 20260812143407), so a note's `agent_id` records **who wrote it**, and the trail is only worth anything if nothing — an admin's reassignment included — can change that after the fact. A read policy widens who can see a note without changing what it says or who said it. It would be a cross-book read, so it needs the same care as the other cross-book paths (`docs/claude/rpcs-profiles-audit.md`): `owner_type` in the predicate (ids collide across types), `is_active_agent()` on the branch, and a test that a rep who owns merchant 7 does not see notes on lead 7.

## `check_duplicates()` is a cross-book read with no audit and no limit

- **Severity:** Low to Medium (noticed while fixing `accounts_in_city`, phase 5; not in the review).
- **Evidence:** `check_duplicates()` is `security definer` over every rep's book, like `accounts_in_city()` was before 20261023120000. It answers free-text inputs (business name, phone, email, address, MID…) with a redacted match list, and writes nothing to `audit_log`. A rep can loop over candidate names or phone numbers and learn which exist in someone else's book. Its output is narrower than `accounts_in_city`'s (it warns about a match, it does not list a city's accounts), and the function must never become a block.
- **Suggested fix:** the phase 5 pattern: one `audit_log` row per call (`check_duplicates:<fields supplied>`, no values), and a per-rep hourly limit counted from those rows under an advisory lock. Size the limit from real use first; the pre-app and lead forms call it on blur, so it is far chattier than the city search.

## A forced password change can be skipped by calling `clear_must_change_password()` directly

- **Severity:** Low (only the account's own holder can do it, and the password they keep is one an admin already knows; it weakens a hygiene control, not access control).
- **Evidence:** `clear_must_change_password()` (`supabase/migrations/20260811094500_manage_users.sql:43`, spec `docs/tapswipe_crm_schema.sql:272`) is `security definer` and runs `update profiles set must_change_password = false where id = auth.uid()` with no other condition. It is granted to `authenticated` (lines 142-143). It does not check that the password changed, because it cannot: the database has no view of GoTrue's password events. The only caller in the app is `components/update-password-form.tsx:66`, after `auth.updateUser({ password })` succeeds, but nothing ties the two. A user signed in with an admin-issued temporary password can `POST /rest/v1/rpc/clear_must_change_password` and `ForcePasswordChangeGate` (`app/(app)/layout.tsx:87-92`) stops redirecting them, so the temporary password stays their working credential. The gate is also UI-only: the flag is read by `requireUser()` in the `(app)` layout and nowhere in RLS, so even with the flag set the temporary password already works against PostgREST and the Edge Functions.
- **Suggested fix:** clear the flag server-side, from the password change itself, instead of from a client call. Options in this repo's terms: (a) an Edge Function `change-own-password` that calls `auth.admin.updateUserById(caller, { password })` and then clears the flag as service role, with `clear_must_change_password()` revoked from `authenticated`; or (b) keep the RPC but have it compare `auth.users.updated_at`/`encrypted_password` against a value captured when `admin-reset-password` set the flag (store it on `profiles`), refusing to clear when the hash has not changed. (a) is simpler and puts the ordering the form's comment describes in one place. If the flag should also bind data access, it would have to enter `is_active_agent()`, which is a bigger change than this finding warrants.

## Hosted Auth settings that differ from, or are not covered by, `config.toml`

- **Severity:** Low to Medium (unknown until checked: the hosted values are not in the repo, and `tests/deployed/auth-config.test.ts` asserts only sign-up, providers and anonymous sign-in).
- **Evidence:** `supabase/config.toml` governs the local stack only, and has `secure_password_change = false` (line 244), `minimum_password_length = 6` (186), `password_requirements = ""` (189), `[auth.mfa.totp]` and `[auth.mfa.phone]` both `enroll_enabled = false` / `verify_enabled = false` (330-336), and `[auth.rate_limit]` `sign_in_sign_ups = 30`, `token_verifications = 30`, `token_refresh = 150`, `email_sent = 2` (201-213). `lib/passwords.ts:22` matches the 6-character floor in the browser. What each means on the hosted projects, and why to check it:
  - `secure_password_change`: when on, GoTrue requires a recent sign-in (or a reauthentication nonce) before `updateUser({ password })`. Off means a stolen session cookie can change the password and lock the owner out. The forced-change flow updates right after sign-in, so turning it on should not break it (unverified on the hosted projects).
  - Minimum length and character requirements: reps choose their own password after the forced change; 6 with no requirements is the GoTrue floor. Leaked-password protection is a hosted-only setting to check at the same time.
  - MFA (TOTP): an admin account reads every row in the company, including full SSNs and bank numbers through `read-pre-app-secrets`. There is no MFA in the app (no enrol or challenge UI), so enabling the factor in the dashboard alone changes nothing until the app asks for AAL2.
  - Rate limits: `sign_in_sign_ups` and `token_verifications` are the password-guessing and OTP-guessing ceilings per IP; `email_sent` bounds reset mail.
- **Suggested fix:** read the values in each hosted project's Dashboard (Authentication > Providers > Email for secure password change and password rules; Authentication > Rate Limits; Authentication > Multi-Factor), or with a Management API `GET /v1/projects/{ref}/config/auth`, and record them. Change any of them only with a targeted `PATCH .../config/auth` naming the one field, or in the Dashboard. **Never `npx supabase config push`**: it would push this file's local-dev `[auth]` block (Site URL `http://127.0.0.1:3000`, the redirect list, `email_sent = 2`, confirmations off) to the project. Then add the settings the team decides on to `tests/deployed/auth-config.test.ts`, which already reads `/auth/v1/settings` for both projects; note that endpoint does not expose rate limits or `secure_password_change`, so those need the Management API or a manual record.

## `admin-reset-password` can target another admin, and leaves the target's sessions alive

- **Severity:** Low to Medium (needs an admin, who already reads everything; the session half matters most when the reset is used to recover a compromised account).
- **Evidence:** `supabase/functions/admin-reset-password/index.ts` checks that the caller is an active admin (lines 44-49) and that the target row is visible (69-77), then sets a new password with `auth.admin.updateUserById(userId, { password })` (82-85) and returns it to the caller (110-118). There is no check on the target's role, and the comment at 66-68 rules out only a self-target guard. So admin A can reset admin B, receive B's temporary password, and sign in as B; audit rows written in that session name B as the actor. Nothing in the function revokes B's refresh tokens. `deactivate-user` documents the same gap (lines 146-150): `auth.admin.signOut()` needs the target's own JWT. GoTrue's admin password update does not, as far as I know, end existing sessions (not verified against the running stack), so a reset done because an account was compromised leaves the attacker's session refreshing for as long as it lives. The UI (`components/user-row-actions.tsx:75-86`) offers the reset on every row.
- **Suggested fix:** two separate changes. (1) Refuse an admin target unless the caller is the target (a 403 is fine here: the caller is already an admin, so there is no id oracle to protect), and leave admin-on-admin resets to the Supabase Dashboard, where they are a deliberate act by the project owner. Disable the control on admin rows in `components/user-row-actions.tsx`. (2) Revoke sessions on reset: a `security definer` SQL function callable only by `service_role` (`revoke all … from public`; `grant execute … to service_role`) that runs `delete from auth.sessions where user_id = $1` (refresh tokens cascade from sessions), called after `updateUserById` succeeds and before the response. Already-issued access tokens still live up to `jwt_expiry` (3600 s); say so in the UI. Test in `tests/live/`: a refresh with the target's old refresh token fails after the reset.

## Inline viewing trusts the uploader's mime type, recorded separately from the stored object's

- **Severity:** Low (uploads are admin-only in both functions; the risk is a hostile or compromised admin, or a crafted request, not a rep).
- **Evidence:** both `business-document-file-url` (`INLINE_SAFE_TYPES`, lines 56-63; check at 131-134) and `marketing-material-file-url` (66-73; check at 176-179) decide inline vs attachment from the **row's** `mime_type`. That value comes from the upload request body (`body.mime_type`, `business-document-file-url/index.ts:189-192`, `marketing-material-file-url/index.ts:227-230`), which the browser fills from `file.type` (`components/business-document-upload.tsx:80`, `components/marketing-material-upload.tsx:91`). The **object's** Content-Type, which is what Storage actually serves, is set independently by the upload to the signed URL: `uploadToSignedUrl(path, token, file)` with no `contentType` sends multipart, and the part's type is again the browser's `file.type` (`@supabase/storage-js` `uploadToSignedUrl`). Nothing compares the two, and no bucket sets `allowed_mime_types` (`20261009170000_storage_buckets.sql` sets only `file_size_limit`). An admin calling the function with `mime_type: "application/pdf"` and then uploading the object as `text/html` (or `image/svg+xml`) gets an inline signed URL that serves HTML on the Storage origin, with `window.opener` to the CRM tab unless the opener is cut (`docs/claude/reference-data-and-marketing.md`). Through the normal UI the two values agree, because both are `file.type`; the browser's guess is extension-based, so a renamed file gets a passive type and renders harmlessly.
- **Suggested fix:** make the stored object the source of truth. In the download branch, read the object's metadata (`storage.from(bucket).info(file_key)` or a `list` on the folder, as service role after authorization) and apply `INLINE_SAFE_TYPES` to the object's `contentType`, not the row's; force attachment when they disagree. Belt and braces: set `allowed_mime_types` on `business-documents` and `marketing-materials` if the libraries can live with a fixed list (hosted buckets need it set out-of-band, like the size limit). Pin it in `tests/live/business-documents.test.ts` and `tests/live/marketing-materials.test.ts`: a row saying PDF over an object stored as `text/html` signs as attachment.

## Quote line items can be added to a sent, accepted or superseded quote

- **Severity:** Low (a rep can only change their own proposals, but it breaks the "a version is what it said when it was sent" rule the design rests on).
- **Evidence:** the insert policy on `quote_line_items`, "insert via own quote" (`supabase/migrations/20261002194500_quotes.sql:231-241`, unchanged since), checks only that the parent quote is the caller's (or that the caller is admin). It does not read `quotes.status` or whether the quote is the newest version of its group. The table-level grant is `select, insert` (line 527). The only trigger, `snapshot_quote_line_item()` (`20261007150000_quotes_merchant_owner_and_price_lock.sql:165-219`), fixes the price fields but does not look at the parent. So a rep can `POST /rest/v1/quote_line_items {"quote_id": <a sent or accepted version>, "product_id": …, "quantity": …}` and the printed proposal for that version (`lib/quote-proposal.ts` reads its line items) changes after it was sent, at today's list price. The same works on any older version in the group. `docs/claude/proposals-and-catalog.md` says changing a line is "the edit that is supposed to produce a new version"; adding one is not covered.
- **Suggested fix:** extend the BEFORE INSERT trigger (or add a second definer trigger, `set search_path = public, pg_temp`) to refuse a line item unless the parent quote was inserted in the **same transaction** — `create_quote_version()` (invoker, `20261009150000_proposals.sql:168`) writes the quote and its items in one call, so `parent.xmin = pg_current_xact_id()::xid` admits exactly that path. Raise `PT409` with a sentence ("Line items are fixed once a version is saved. Create a new version instead."). Tests in `tests/rls/`: a rep adding to their own draft from a separate statement is refused; `create_quote_version` still works; an admin is refused too.

## Foreign keys can point at records the inserting rep cannot see

- **Severity:** Low (no read of the other rep's record follows from it; it is an integrity gap with one small disclosure: whether an id exists).
- **Evidence:** the standard insert/update policies (`20260805103000_add_is_active_agent_and_profile_self_service.sql`) check only `agent_id = auth.uid() and is_active_agent()`. No policy or trigger reads the client-supplied link columns on these tables, all writable by `authenticated` at table level (`20260805200000_grant_data_api_roles.sql`):
  - `pre_apps.lead_id` (insert own / update own on a draft). `pre_apps_guard_transitions()` (`20260916104500`) checks status and `date_submitted` only. A rep can point their pre-app at another rep's lead. `dashboard_counts` counts a lead as active only when no pre-app references it (`docs/tapswipe_crm_schema.sql:8888-8891`), so the other rep's lead drops out of the admin's Leads figure.
  - `ghost_sheets.lead_id` (insert own / update own). `convert_ghost_sheet_to_lead()` sets it, but a rep can also write any lead id directly, which marks the sheet converted against someone else's lead.
  - `support_tickets.merchant_id` (insert own). A rep can file a ticket against another rep's merchant; an admin sees it listed as that merchant's ticket.
  - `notes` and `tasks` `owner_type` + `owner_id` (insert own; no FK at all, polymorphic). A rep can attach a note or task to another rep's merchant, lead, pre-app or ghost sheet. The owning rep never sees it (RLS is on the note's own `agent_id`), but an admin viewing that record does, in the record's own timeline.
  - In every case a foreign-key violation (`23503`) versus success tells the rep whether that id exists — serial ids, so roughly "how many leads or merchants the company has".
  - Already closed, for contrast: `quotes` ("insert own, linked only to what the caller can see", `20261009150000_proposals.sql:78`) and `marketing_material_events` ("insert own via own lead", `20261002181500`).
- **Suggested fix:** the `quotes` pattern, per table: add `and (lead_id is null or exists (select 1 from leads where leads.id = lead_id))` (and the `merchants` equivalent) to the insert and update WITH CHECK, so the reference must be visible to the caller under RLS. For `notes`/`tasks`, a CASE on `owner_type` with one `exists` per type, which also stops an id collision across types. Admins pass through RLS's `is_admin()` branch on the referenced tables, so their writes are unchanged. Tests in `tests/rls/`: a rep inserting each link to another rep's record is refused; to their own, admitted. Check existing rows first for any that would now fail an UPDATE.

## Bug reports can be filed already resolved, and attributed to an admin

- **Severity:** Low (a rep can only hide or mislabel their own report).
- **Evidence:** "insert own" on `bug_reports` (`supabase/migrations/20260812175050_bug_reports.sql:69`; spec `docs/tapswipe_crm_schema.sql:2016-2017`) checks `agent_id = auth.uid() and is_active_agent()` only, and `authenticated` holds a table-level `insert` (line 89). So a rep can `POST /rest/v1/bug_reports` with `status: "resolved"` or `"dismissed"`, any `resolved_at`, any `resolved_by` (an admin's uuid), and a back-dated `created_at`. The report skips the open queue and reads as closed by that admin. `bug_reports_audit_cross_agent` (line 103) logs only when the actor differs from `agent_id`, so the insert is silent. The app's own insert (`components/bug-report-bubble.tsx`) (lines 95-99) sends only `agent_id`, `page` and `description`, so nothing legitimate needs the other columns.
- **Suggested fix:** column-level insert grant: `revoke insert on bug_reports from authenticated; grant insert (agent_id, page, description) on bug_reports to authenticated;` — the same "immutable is a GRANT" rule as `quotes.status`. `status`, `resolved_at` and `created_at` then take their defaults, and `resolved_by` stays null. Optionally add `status = 'open' and resolved_by is null` to the policy as a second layer. Test in `tests/rls/`: an insert naming `status` fails with `permission denied for column`.

## Admins see full SSNs, bank numbers and the RP password as soon as the step opens

- **Severity:** Low to Medium (by design admins may read them; the gap is that reading needs no deliberate act, and the audit row cannot tell a look from a glance).
- **Evidence:** `components/pre-app-steps/secrets-step.tsx` calls `read-pre-app-secrets` on mount (`refresh` in a `useEffect`, lines 108-125). For an admin the function returns plaintext (`supabase/functions/read-pre-app-secrets/index.ts:136`, `154-155`, `165-171`), and `OnFile` renders it straight into the page (`secrets-step.tsx:212`, `244`, `265-266`, `300-302`, `350-353`: "SSN: on file — 123-45-6789"). There is no click-to-reveal and no masking. Every mount writes `read_pre_app_secrets:full` to `audit_log` (line 85), so an admin opening the tab to check what is on file logs the same row as one copying the numbers out. The values sit in React state and on screen for anyone shoulder-surfing or on a screen share. Positive: the print page and the review step deliberately do not call the function (`app/(app)/merchants/[id]/print/page.tsx:26-29`, `review-step.tsx:36-46`).
- **Suggested fix:** return last-four to everyone by default, and add an explicit `reveal: true` request (one field at a time, e.g. `{ pre_app_id, reveal: "ssn", owner_id }`) that only an admin may make. Audit it as `read_pre_app_secrets:reveal:<field>`, and keep the existing `last4` row for the default load. In the UI, a "Show" button per field that hides the value again after a short timeout or on blur. Pin in `tests/live/pre-app-secrets.test.ts`: an admin's default read carries no full value, a reveal does, and a rep's reveal is refused.

## Raw database error text still reaches users on most forms

- **Severity:** Low (information disclosure to signed-in users only; no data, only schema names and Postgres wording).
- **Evidence:** `lib/db-errors.ts` `friendlyDbError()` maps five SQLSTATEs (`23505`, `23503`, `23514`, `22003`, `22P02`) and passes every other message through unchanged (lines 47-49), which includes `42501` ("permission denied for table …", "new row violates row-level security policy for table …"). Its header says it is applied only to the busiest forms; 16 files use it. 24 call sites still put `error.message` straight into the UI, e.g. `components/notes-panel.tsx:65`, `tasks-panel.tsx:72`, `ticket-replies-panel.tsx:61`, `bug-report-bubble.tsx:102`, `pre-app-decision.tsx:65,85,105`, `residual-commit-button.tsx:56`, `payout-figure-cell.tsx:129`, `global-search.tsx:71`, `user-row-actions.tsx:107` (full list: `grep -rn "Error(\w*Error.message" components`). Edge Functions do the same server-side: e.g. `admin-reset-password/index.ts:89` returns `Could not reset the password: ${passwordError.message}` and `business-document-file-url/index.ts` returns `Could not create the document: ${createError?.message}`, which `lib/edge-functions.ts` then shows. Our own `PT4xx`/`P0001` messages are written for people and are fine to pass through.
- **Suggested fix:** route every remaining call site through `friendlyDbError`, and change its fallthrough to pass a message through only for `P0001` and `PT4xx` codes; anything else becomes the caller's `fallback` with the raw text sent to `console.error`. Add `42501` to the map ("You don't have access to do that."). In the Edge Functions, log the GoTrue/PostgREST message and return a fixed sentence. A unit test on `friendlyDbError` pins the fallthrough rule.

## Residual and rep-import parsers: no row cap on the XLSX path, and two quadratic regexes

- **Severity:** Low (both functions are admin-only; the worst case is one failed invocation that hits the Edge runtime's memory or CPU limit).
- **Evidence:**
  - `stage-user-import` caps input before parsing (`MAX_SOURCE_BYTES = 512 KiB`, `index.ts:50`, checked at 150) and rows after parsing (`MAX_IMPORT_ROWS = 200`, `_shared/user-imports.ts:85`, 470). Fine.
  - `parse-residual-import` has no cap of its own. It downloads the whole object (`index.ts:107`), runs `XLSX.read` with no `sheetRows` (124-130), and `sheet_to_json` with `defval: null, blankrows: true` (138-150), then stages every row. The only bound is the bucket's 50 MiB `file_size_limit` (`20261009170000_storage_buckets.sql:31`). XLSX is zip-compressed, so 50 MiB can expand far beyond the function's memory, and a sheet whose declared range is huge but mostly empty may make `blankrows: true` materialise every blank row (SheetJS behaviour with a large `<dimension>` ref: not verified here).
  - Regexes: none is exponential. Two are quadratic on a long run of matching characters: `/^-?\d*\.?\d+$/` in the money parser (`_shared/residuals.ts:257`; `\d*` and `\d+` overlap, so a long digit string ending in a non-digit backtracks O(n²)), and `/[:.]+$/` in header normalisation (`residuals.ts:163`, `user-imports.ts:313`; a long run of `:` or `.` not at the end). `/\s*#\s*/g` (`residuals.ts:162`, `user-imports.ts:312`) would be quadratic too, but runs after `/\s+/g` collapses whitespace. An Excel cell holds at most 32,767 characters, so the worst case is around 5×10⁸ steps per cell — seconds, not hours (estimate, not measured).
- **Suggested fix:** in `parse-residual-import`, pass `sheetRows: MAX_RESIDUAL_ROWS + header allowance` to `XLSX.read` and refuse a file with more rows (size the cap from the largest real processor file, e.g. 20,000), and refuse a blob over a smaller byte cap before reading it. In `_shared/residuals.ts`, reject a cell over a sane length (e.g. 64 chars for a number, 200 for a header) before any regex, and rewrite the number test as `/^-?(?:\d+(?:\.\d*)?|\.\d+)$/`, which does not overlap. Unit tests in vitest (the parser is already imported there): a 32,767-character digit cell parses as bad in under 50 ms.

## Residual export pages on an order that is not unique

- **Severity:** Low (wrong totals in a commission export, not a disclosure; only shows up when tied rows straddle a page boundary).
- **Evidence:** `supabase/functions/export-residuals/index.ts:92-100` reads `rep_payout_rows` in pages of `PAGE_SIZE` with `.order("period" desc).order("agent_id").order("mid").range(…)`. `(period, agent_id, mid)` is unique only for `line_kind = 'import'` (`rep_payout_rows_import_merge_key`, `20261016160000_import_merge_key.sql:108-110`); adjustment lines (`20261014140000_shared_lines.sql`, `20261016161000_share_corrections.sql`) can share all three values with an import line and with each other. Postgres does not promise a stable order among ties across separate queries, so two rows tied at a page boundary can come back as one row twice and the other not at all. The export would look complete. Each page is also its own query, so a write between pages can shift rows (a smaller window; exports run rarely). `parse-residual-import` does it right: `.order("id")` before `.range` (`index.ts:327`).
- **Suggested fix:** add `.order("id", { ascending: true })` as the last sort key. For a consistent snapshot as well, move the read into an invoker SQL function returning the rows in one statement (keeps RLS as the authorization, per the rule that this function never uses `supabaseAdmin`), or page by keyset on `(period, agent_id, mid, id)`. Test in `tests/live/`: with `PAGE_SIZE` lowered and two tied rows at the boundary, the export has every row exactly once.

## Most `security definer` functions set `search_path = public` without `pg_temp`
